# Чек-лист выпуска новой версии

Составлен по содержимому скриптов, а не по памяти: `CMakeLists.txt`,
`.github/workflows/{gh-release,Linux-pack,Windows-pack,MacOS-pack}.yml`,
`misc/LATEST_RELEASE_BODY`, `misc/change_log_prepend.sh`, `ChangeLog`,
`snap/snapcraft.yaml`,
`packaging/`, а также `familiar-web` (`publish-images.yml`,
`frontend/src/lib/releases.ts`, `frontend/src/app/releases/page.tsx`,
`deploy/familiar-update.timer`).

## Что откуда берётся

**Номер версии берётся не из тега.** Единственный источник —
`CMakeLists.txt:3`, `set(FAMILIAR_VERSION ...)`. Каждый пакетный job
вытаскивает его оттуда своим `grep` (`Linux-pack.yml:91,166,228`,
`Windows-pack.yml:111`, `snap/snapcraft.yaml:49`), и из него же
складываются имена всех артефактов. Тег участвует только в двух вещах:
запускает workflow и определяет, к какому релизу прикрепить файлы
(`if: startsWith(github.ref, 'refs/tags/')`).

Отсюда главный риск: тег `v0.0.18` при незабытом `0.0.17` в CMakeLists
даёт релиз v0.0.18, внутри которого лежат файлы
`familiar-0.0.17-x86_64.AppImage` и `familiar-0.0.17-win64.zip`. Ничего
не падает — на сайте просто появится новая версия со старыми именами
файлов.

**Шаблон тега:** `v[0-9].[0-9]+.[0-9]+`. Мажор — одна цифра, `v10.0.0`
под шаблон не попадёт.

**Текст релиза:** `misc/LATEST_RELEASE_BODY` → `bodyFile` в
`gh-release.yml` → тело GitHub-релиза → страница `/releases` на сайте.
Сайт рендерит его как GFM-markdown, сам вырезает `(#123)` и понимает
старый формат «`Changes:` + пункты с отступом в два пробела»
(`releases/page.tsx:13-24`). То есть markdown писать можно.

**Что вообще выкладывается в бете** (после коммита `fd0a915`):
Linux AppImage и Windows portable ZIP. Отключены через `if: ${{ false }}`
— tarball, deb, rpm, flatpak, snap; Windows installer убран из матрицы
(`type: [portable]`); macOS переведён на `workflow_dispatch` и на тег
не реагирует.

## 1. До тега

- [ ] Поднять `set(FAMILIAR_VERSION ...)` в `CMakeLists.txt:3` до той же
      версии, что будет в теге. **Это главный пункт списка.**
- [ ] Перезаписать `misc/LATEST_RELEASE_BODY` — это публичный ченджлог.
      Сейчас он устарел: перечисляет PR до #101, тогда как в HEAD уже
      #115 (telemetry), #116 (annotation shortcuts), #117 (phase 1 bug
      fix). `change_log_prepend.sh` этот файл не трогает, но формат
      пунктов у них один и тот же (`  - <тема коммита>`), так что блок
      переносится из `ChangeLog` как есть, под строкой `Changes:`.
- [ ] Нарастить `ChangeLog` скриптом `misc/change_log_prepend.sh`,
      передав ему предыдущий тег:
      `./misc/change_log_prepend.sh v0.0.17`. Он берёт
      `git describe --tags` как заголовок, собирает `git log` в формате
      `  - <тема коммита>` от переданного тега до HEAD и дописывает
      результат сверху существующего `ChangeLog`. Из CI его не вызывает
      никто — только руками. Три проверенные ловушки:
      - **Аргумент обязателен.** Без него диапазон превращается в
        `..HEAD`, git читает это как `HEAD..HEAD`, и список коммитов
        выходит пустым — молча, без ошибки.
      - **Запускать через `sh`, не через `bash`.** Разделители в скрипте
        написаны как `echo "==\n"`, и перевод строки получается только
        потому, что `/bin/sh` здесь — dash. Под bash в файл попадёт
        буквальное `\n`.
      - **Тег должен уже существовать на HEAD.** `git describe --tags`
        без тега на HEAD выдаёт не версию, а `v0.0.17-9-gfd0a915`, и
        именно это уедет в заголовок.
- [ ] Решить, помечать ли релиз как pre-release. Сейчас `gh-release.yml`
      не ставит `prerelease`, то есть бета выйдет полноценным релизом и
      станет для всех самой свежей загрузкой на `/download`. Сайт умеет
      показывать плашку «Pre-release», если GitHub так релиз пометил.
- [ ] Прогнать тесты на том коммите, который будет помечен тегом.
      `build_cmake.yml` ловит только PR и пуши в `main`, по тегу он не
      запускается вообще — поэтому в каждом пакетном workflow есть свой
      гейт `run-tests`, и при падении тестов не соберётся ни один
      артефакт.
- [ ] Косметика, если захочется: версия в примере телеметрии
      `README.md:186`, placeholder в
      `.github/ISSUE_TEMPLATE/bug-report.yaml:22`.

Разово, до первого релиза с автосборкой сайта:

- [ ] `notify-site.yml` влит в `main`. Версия workflow берётся из
      коммита, на который указывает событие, а для релиза это помеченный
      тегом коммит — если файла там нет, связка просто не сработает.
- [ ] В секретах репозитория клиента лежит `SITE_DISPATCH_TOKEN` (токен
      с правом Contents: write на `try-hard-factory/familiar-web`).

## 2. Тег

Здесь есть «курица и яйцо»: скрипту нужен тег на HEAD, а запись в
`ChangeLog` должна оказаться внутри помеченного коммита. В v0.0.17 так и
получилось — проверено, `git show v0.0.17:ChangeLog` начинается с
«Version v0.0.17», то есть запись лежит в самом помеченном коммите
`ab726ae` «New version v0.0.17». [Вывод] Воспроизводится это такой
последовательностью:

- [ ] закоммитить поднятую версию и новый `misc/LATEST_RELEASE_BODY`;
- [ ] поставить тег локально;
- [ ] прогнать `change_log_prepend.sh` с предыдущим тегом;
- [ ] сложить `ChangeLog` в тот же коммит через `git commit --amend`;
- [ ] переставить тег на изменённый коммит (`git tag -f`);
- [ ] запушить ветку и тег.

Короткий вариант без возни с тегами: прогнать скрипт до тега и поправить
строку заголовка руками — она там одна.

## 3. Пока идёт CI (~20 минут)

Запускаются три workflow сразу: `Create Release`, `Packaging(Linux)`,
`Packaging(Windows)`. По v0.0.17: релиз создан через 5 секунд после
старта, Linux закончил через 12 минут, Windows — через 20.

- [ ] `Packaging(Linux)` → `Build AppImage` зелёный.
- [ ] `Packaging(Windows)` → `VS 2022 x64-portable` зелёный.

## 5. Сайт — сам

- [ ] `Notify site` в репозитории клиента дождался упаковки и отправил
      запрос.
- [ ] В `familiar-web` запустился `Publish for client release <тег>`.
- [ ] Через ≤15 минут после публикации образа VPS подхватил его по
      `familiar-update.timer`.
- [ ] `/download` показывает новую версию, `/releases` — новый ченджлог.

Если руками запускался `Packaging(MacOS)`, его `.dmg` в это ожидание не
попадает: `notify-site` ждёт только запуски с `event=push`, а ручной
запуск — это `workflow_dispatch`. После загрузки `.dmg` нужно запустить
`Notify site` вручную, указав тег, иначе на сайте не будет кнопки macOS.

Тот же ручной запуск — лекарство на все случаи «ассеты релиза
поменялись после сборки».

## Известные пробелы (не блокеры выпуска)

- Контрольные суммы теперь выкладываются в релиз для обоих бета-файлов
  (AppImage и Windows portable). У отключённых джобов — tarball, deb,
  rpm, flatpak, snap, Windows installer — суммы по-прежнему считаются,
  но в `files:` не попадают: при включении любого из них строку
  `.sha256sum` нужно дописать туда же. У installer-джоба вдобавок та же
  беда с абсолютным путём внутри файла суммы, которая исправлена для
  portable (`Windows-pack.yml`, шаг «SHA256Sum of Windows installer»).
- Сумма, лежащая на том же сервере, что и файл, защищает от битой
  загрузки, но не от подмены: подменивший ассет подменит и сумму рядом.
  Настоящая защита — подпись (Authenticode / Developer ID / GPG) или
  artifact attestations GitHub, и ни того, ни другого пока нет.
- Windows-джоб вдобавок заливает посчитанные `.sha256sum` на внешний
  сервис через `scripts/upload_services/transferwee.py` и печатает
  ссылку в лог (`Windows-pack.yml`) — наследие ежедневных сборок
  Flameshot. Оставлено как есть.
- Подписи нет нигде: Windows Authenticode, macOS Developer ID, GPG для
  Linux.
- Своего AppStream metainfo у приложения нет.
  `packaging/linux/org.tryhardfactory.Familiar.xml` — это MIME-описание
  `.fml`, не metainfo.
- Черновики пакетов для сторонних каналов держат версию 0.0.16 и
  placeholder-вместо-sha256: `packaging/aur/PKGBUILD`,
  `packaging/choco/`, `packaging/homebrew/familiar.rb`. Пока эти каналы
  не запущены, на выпуск они не влияют. У `packaging/rpm/familiar.spec`
  версия тоже 0.0.16, но её подменяет сам workflow
  (`Linux-pack.yml:264`), так что это не ручной шаг.
- Самообновления в сборках нет.
