# Чек-лист выпуска новой версии

## Что где лежит

| Что | Где | Кто меняет |
|---|---|---|
| Номер версии | `CMakeLists.txt:3`, `set(FAMILIAR_VERSION ...)` | руками |
| Текст релиза на GitHub и на сайте | `misc/LATEST_RELEASE_BODY` | руками, копипастой из `ChangeLog` |
| История изменений | `ChangeLog` | скриптом `misc/change_log_prepend.sh` |
| Имена файлов артефактов | из `FAMILIAR_VERSION`, не из тега | — |
| Сборка сайта | сама, по событию публикации релиза | — |

Шаблон тега: `v[0-9].[0-9]+.[0-9]+`.

## Выпуск

1. Влить всё, что должно попасть в релиз, в `main`. Перейти на `main`,
   `git pull`.

2. Поднять версию в `CMakeLists.txt:3`.

3. Закоммитить:

   ```sh
   git commit -am "New version v0.0.18"
   ```

4. Поставить тег локально — он нужен скрипту на следующем шаге:

   ```sh
   git tag v0.0.18
   ```

5. Нарастить `ChangeLog`, передав **предыдущий** тег:

   ```sh
   sh misc/change_log_prepend.sh v0.0.17
   ```

   Три условия, иначе результат молча неправильный:
   - аргумент обязателен (без него список коммитов выйдет пустым);
   - запускать через `sh`, не `bash` (под `bash` в файл попадёт
     буквальное `\n`);
   - тег уже должен стоять на HEAD (шаг 4), иначе в заголовок уедет
     `v0.0.17-9-gfd0a915` вместо версии.

6. Скопировать свежий блок пунктов из `ChangeLog` в
   `misc/LATEST_RELEASE_BODY`, под строку `Changes:`. Номера PR
   оставлять — на GitHub это ссылки, на сайте они вырезаются при
   рендере.

7. Сложить `ChangeLog` и `LATEST_RELEASE_BODY` в тот же коммит и
   переставить тег:

   ```sh
   git commit --amend --no-edit
   git tag -f v0.0.18
   ```

8. Запушить:

   ```sh
   git push origin main
   git push -f origin v0.0.18
   ```

## Что происходит само

| Когда | Что |
|---|---|
| сразу | `Create Release` создаёт релиз с текстом из `misc/LATEST_RELEASE_BODY` |
| ~12 мин | `Packaging(Linux)` выкладывает AppImage и его `.sha256sum` |
| ~20 мин | `Packaging(Windows)` выкладывает portable ZIP и его `.sha256sum` |
| после упаковки | `Notify site` дожидается её и дёргает familiar-web |
| +2 мин | в familiar-web идёт `Publish for client release v0.0.18` |
| ≤15 мин | VPS подхватывает образ по `familiar-update.timer` |

## Проверить

- [ ] В релизе четыре файла: AppImage, Windows ZIP и два `.sha256sum`.
- [ ] Версия в именах файлов совпадает с тегом. Если нет — забыт шаг 2.
- [ ] Текст релиза — тот, что из `LATEST_RELEASE_BODY`.
- [ ] `/download` показывает новую версию, `/releases` — новый ченджлог.

## Если что-то не так

- **Сайт не обновился.** Запустить `Notify site` в репозитории клиента
  вручную, указав тег. То же самое — если ассеты релиза поменялись после
  сборки.
- **Руками запускался `Packaging(MacOS)`.** Его `.dmg` в ожидание не
  попадает (`Notify site` ждёт только запуски с `event=push`), так что
  после загрузки `.dmg` нужен ручной запуск `Notify site`.
- **Упал пакетный джоб.** `Notify site` всё равно пересоберёт сайт — он
  покажет те загрузки, которые выложились. После перезапуска джоба
  дёрнуть `Notify site` руками.
- **Тесты упали.** Ни один артефакт не собирается: в каждом пакетном
  workflow стоит гейт `run-tests`. `build_cmake.yml` по тегу не
  запускается вообще, только по PR и пушу в `main`.

## Что в бете не выкладывается

AppImage и Windows portable ZIP — всё. Отключены через `if: ${{ false }}`
tarball, deb, rpm, flatpak, snap; Windows installer убран из матрицы;
macOS переведён на ручной запуск. Включать — снимать `if` и добавлять в
`files:` строку `.sha256sum` (у installer-джоба заодно поправить
абсолютный путь в шаге подсчёта суммы, как сделано для portable).

## Пробелы

- Подписи нет: Authenticode, Developer ID, GPG. Контрольная сумма рядом
  с файлом спасает от битой загрузки, но не от подмены.
- Своего AppStream metainfo нет (`packaging/linux/*.xml` — это
  MIME-описание `.fml`).
- Черновики сторонних каналов держат 0.0.16 и placeholder вместо
  sha256: `packaging/aur`, `packaging/choco`, `packaging/homebrew`. Пока
  каналы не запущены, на выпуск не влияют. У `packaging/rpm` версию
  подменяет сам workflow.
- Самообновления в сборках нет.
